# Triton Optimization

This note collects Triton-specific optimization guidance that complements the
generic CUDA notes in `docs/`.

## Main Levers

- Tile sizes: tune `BLOCK_M`, `BLOCK_N`, `BLOCK_K` per shape family.
- Scheduling: tune `num_warps`, `num_stages`, persistent kernels, swizzle, and
  split-K strategies.
- Memory access: improve coalescing and expose alignment with
  `tl.multiple_of` and `tl.max_contiguous`.
- Fusion: prefer fused epilogues and single-pass reductions when register
  pressure permits.
- Specialized paths: use `tl.dot` for tensor-core lowering, `tl.exp2` for
  softmax-style exponentials, and online reductions for attention / norm
  kernels.

## Tile and Block Tuning

Tile shape is the main Triton performance knob because it controls:

- grid size and exposed parallelism
- register footprint of the accumulator and temporaries
- shared-memory reuse generated by the compiler
- arithmetic intensity

Typical rules:

- large GEMMs usually prefer larger `BLOCK_M / BLOCK_N`
- small GEMMs often need smaller tiles to avoid under-utilization
- very large `BLOCK_K` can improve reuse but often raises register pressure

Treat tile size, `num_warps`, and `num_stages` as a coupled decision rather than
independent toggles.

## Autotune Strategy

Use `triton.autotune` for shape families, not as a substitute for thinking.

Practical guidance:

- keep the candidate set small and architecture-aware
- use `key=[...]` to bucket by the dimensions that truly change the optimum
- separate "small problem" and "large problem" configs instead of expecting one
  set to cover both

A large autotune table slows down cold-start and complicates debugging. Start
with a few plausible configs, then expand only where profiling justifies it.

## Memory Access Patterns

### Coalescing

Ensure the contiguous dimension is the one expanded across the fast-moving lane
dimension in pointer arithmetic.

Bad sign:

- high sectors per request
- low effective bandwidth despite high occupancy

### Alignment Hints

Use compiler hints when you know address properties:

- `tl.multiple_of(ptr_or_index, n)`
- `tl.max_contiguous(index, n)`

These hints often decide whether Triton emits wider vectorized loads or falls
back to narrower instructions.

### Boundary Handling

Use `mask=` and `other=` for tail handling rather than adding divergent control
flow to the hot path.

Masking keeps the steady-state loop regular and is usually easier for Triton to
optimize than a branch-heavy edge path.

## Pipelining and `num_stages`

`num_stages` expresses software pipelining depth for load / compute overlap.

Use it when:

- the kernel has a stable inner loop over tiles
- `long_scoreboard` suggests memory latency is not hidden
- shared-memory budget still allows additional buffering

Tradeoff:

- more stages can improve overlap
- more stages also increase resource pressure and can reduce occupancy

If registers or local memory spike after increasing `num_stages`, undo the
change before looking elsewhere.

## Tensor Core Path

For GEMM-like Triton kernels:

- keep the MMA path on `tl.dot`
- keep inputs in supported low-precision formats where the algorithm allows it
- keep the accumulator in `fp32` unless there is a measured reason to do
  otherwise

Common failure modes:

- accidental promotion to scalar FP32 math
- layouts or shapes that miss the intended tensor-core lowering
- fused epilogues that bloat registers enough to erase the tensor-core gain

## Swizzle, Persistent Kernels, and Split-K

### Swizzle

Grouped ordering or swizzled launch order can raise L2 reuse for large GEMMs.
If large tiles look bandwidth-wasteful despite good arithmetic intensity, the
launch order is worth revisiting.

### Persistent Kernels

Persistent kernels are useful when:

- the number of output tiles is much larger than the number of SMs
- launch overhead and scheduler jitter matter
- cross-tile state reuse is valuable

### Split-K

Split-K is useful when:

- `K` is very large
- `M` and `N` are too small to expose enough parallelism

The cost is reduction overhead, so reserve it for shapes that are clearly
under-occupying the machine.

## Fusion Guidance

Fusion is a major Triton strength, but not every producer / consumer pair should
be fused.

Fuse when:

- global-memory traffic is the dominant cost
- the extra epilogue work reuses the same accumulator
- register growth stays controlled

Avoid or reconsider fusion when:

- occupancy collapses
- local memory or spills appear
- the fused kernel becomes hard to validate numerically

## Numeric and Algorithmic Patterns

Useful fast paths:

- `tl.exp2` instead of `tl.exp` when the algebra allows it
- online softmax for attention-like kernels
- Welford-style one-pass statistics for normalization kernels
- branchless tail handling where practical

These are often algorithmic choices with performance implications, not just
micro-optimizations.

## Diagnostic Flow

1. Check whether the kernel is memory-bound or compute-bound with
   `tools/bench.py`.
2. Use targeted NCU to confirm the dominant stall and resource limiter.
3. If registers or local memory spike, reduce tile size or stages first.
4. If memory traffic dominates, revisit launch order, vectorization, and
   alignment hints.
5. If tensor-core utilization is low for GEMM-like kernels, inspect the `tl.dot`
   path, layouts, and data types.

## What To Record Per Iteration

For Triton kernels, experiment notes should capture:

- tile sizes
- `num_warps`
- `num_stages`
- swizzle or persistent scheduling choice
- whether the kernel is fused
- whether the intended tensor-core path was observed
